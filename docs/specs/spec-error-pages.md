# Error Pages for Every Failed Request, Rendered and Flat

> [Specifications](README.md) ·
> [Rendered error pages decision](../decisions/adr-0045-rendered-error-pages.md) ·
> [Critical-failure observability specification](spec-m9-critical-failure-observability.md)

## Problem

A failure was the only part of the product that was not the product. Rails'
generated files answered 400, 404, 406, 422 and 500 in English, unstyled, with
no link back into the academy — on an app whose default language is Thai. The
statuses a visitor most often meets during a deploy, 502 and 503 and 504, had no
page at all. And a 5xx never showed the request id that SPEC-0020 stamps on the
matching alert, so the one number that would let support find the failure was
the one number the person reporting it could not see.

The page also has to survive what it reports. The application layout reads a
learner's gems, streak and notifications on every screen; rendering a 500
through it means a database outage raises twice and the visitor gets the flat
file anyway.

## Invariants

1. `config.exceptions_app` is the router. A failed request is re-dispatched with
   its path rewritten to its status code, on its original verb.
2. `ErrorsController` inherits `ActionController::Base` and includes only
   `Localization`. No authentication, no authorization, no observability
   callback, no browser gate.
3. Rendering an error page performs no database query, and the error layout
   renders no session-dependent chrome.
4. `HttpError::NAMED` — 400, 403, 404, 406, 422, 429, 500, 502, 503, 504 — have
   copy of their own in both locale files. Any other status in 400..599 renders
   using `error_pages.client` or `error_pages.server`, chosen by whether the
   code is below 500.
5. A status outside 400..599 is not an error page: the route constraint is
   `[45]\d\d`, so `/700` is a routing error like any other unknown path.
6. The response carries the status it describes, `noindex, nofollow`, and
   no-cache.
7. A 5xx page prints `request.request_id`; a 4xx page does not.
8. A failed request whose format is not HTML gets the status and an empty body,
   including when the `Accept` header is what was malformed.
9. `HttpError::STATIC_PAGES` names the flat files in `public/`: 400, 404, 422,
   500, 502, 503, 504, and `406-unsupported-browser.html`, whose name is fixed
   by `allow_browser`.
10. The flat files are generated by `bin/rails error_pages:build` from the same
    `error_pages` copy, print Thai and English together, and reference no
    stylesheet, script or asset the app would have to be running to serve.
11. What is committed in `public/` matches what the generator produces.
12. The live pages are reachable at `/errors/:code` as well as at `/:code`,
    because the flat files shadow the bare paths whenever the static file
    server is on.
13. `/errors` is disallowed in `robots.txt`.

## Acceptance Criteria

- Each of the ten named statuses renders at `/errors/<code>` with that status
  and its own title.
- `/errors/409` renders with status 409 and the client-family title.
- `/errors/700` is a routing error, not a rendered page.
- `/errors/404?lang=en` renders the English title; without the parameter a
  Thai-preferring visitor gets Thai.
- `/errors/404` carries `noindex, nofollow` and a no-cache `Cache-Control`.
- `/errors/500` shows the request id of that request; `/errors/404` shows no
  reference line at all.
- `/errors/500` requested as JSON returns 500 with an empty body.
- `POST /422`, dispatched as `exceptions_app` dispatches it, answers 422.
- `/errors/500` renders with no database query and no session.
- A request for a route that does not exist renders the branded 404 through
  `exceptions_app`, not Rails' generated file.
- Every file named in `HttpError::STATIC_PAGES` exists in `public/` and matches
  the generator's output.
- `public/503.html` contains both the Thai and the English title and no `<link
  rel="stylesheet">` or `<script>`.

## Verification

- `test/controllers/errors_test.rb` covers the rendered pages: every named
  status, the family fallback, the constraint, the language, the robots and
  cache headers, the request id on a 5xx and its absence on a 4xx, the non-HTML
  response, the verb, the absence of queries, and the `exceptions_app` dispatch.
- `test/models/http_error_test.rb` covers the copy fallback in both directions,
  the client/server split, the range clamp, and that every named status has
  `name`, `title` and `body` in both locales.
- `test/lib/error_pages_test.rb` covers the freshness of `public/`, the presence
  of each file, the browser file's fixed name, and that a flat page is
  bilingual and self-contained.
- `test/controllers/crawlers_test.rb` continues to cover `robots.txt`.
- `bin/verify` runs the whole gate.

## Out of scope

The platform's own error page. When Render has no container to route to, nothing
in this repository is asked — the generated 502, 503 and 504 files exist so that
a proxy or maintenance-page configuration has something on-brand to serve, not
because setting that up is part of this slice.

Rate limiting is also unchanged. The six controllers that throttle already
redirect with a flash rather than returning a bare 429, which is a better answer
for a form than any page would be; `error_pages.429` exists for a 429 that
arrives without one.
